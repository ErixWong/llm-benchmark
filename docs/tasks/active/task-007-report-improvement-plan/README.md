# Task-007: 报告改进计划

## 目标

为 benchmark 报告层制定一套可执行的改进计划，重点提升 HTML 报告在信息可信度、结构层次、视觉表达和可维护性方面的质量，同时保持 JSON / Markdown / HTML 三种报告的关键口径一致。

## 范围

- `src/reporter.js`
- 生成产物：`results/**/*.html`、`results/**/*.md`、`results/**/*.json`

## 当前问题摘要

1. HTML 报告未明确展示 token 统计来源（`api-usage` / `api-timings` / `tokenizer`）
2. `outputTokens` 与 `visibleOutputTokens` 并列展示，容易被误解为同一口径
3. 页头缺少结论摘要和报告身份信息，主次层级不清晰
4. 图表标题偏泛，未直接表达“这张图回答什么问题”
5. 失败请求、输入 token 口径等关键信息展示不稳定
6. HTML 模板内联样式过多，后续维护和美化成本高

## 改进优先级

### P0 - 可信度与口径透明

1. 在报告首屏展示 token 来源
2. 明确区分服务端输出 token 与本地可见文本 token
3. 为输入 token、输出 token、TTFT 增加口径说明
4. 保证 JSON / Markdown / HTML 对同一指标的名称和单位一致

### P1 - 信息架构

1. 增加页头摘要结论
2. 重排 KPI 层级：主指标、次级运行信息、图表区分层
3. 固定展示失败请求摘要位
4. 在配置区补齐并发数、采样数、token 统计来源等关键字段

### P2 - HTML 视觉改进

1. 强化页头设计，使报告身份一眼可见
2. 收敛卡片层级，减少“九宫格碎片化”观感
3. 调整颜色与字体对比，让重点指标更突出
4. 优化图例、说明条和图表标题文案

### P3 - 模板与维护性

1. 将大块内联样式抽离为 class
2. 让 HTML 结构和样式职责更清晰
3. 为关键纯函数和渲染逻辑补回归测试

## 实施顺序

1. 先做 `P0`，保证报告口径不误导
2. 再做 `P1`，让报告可读、可判断
3. 然后做 `P2`，提升 HTML 成品质量
4. 最后做 `P3`，降低后续维护成本

## 验收标准

1. 首屏可直接看出 token 来源、主要结论和失败情况
2. `outputTokens` / `visibleOutputTokens` 不再以误导方式并列展示
3. HTML / Markdown 对同一指标的单位与命名一致
4. 至少有一组 reporter 测试覆盖新增关键逻辑
5. 生成的 HTML 报告在桌面端和常见窄屏宽度下都保持可读

## 风险说明

- 报告信息层级重排可能牵涉既有测试快照或文本断言
- 指标命名调整需要同步 Markdown 和 HTML，避免再次分叉
- 如果后续引入更多 token 来源类型，报告说明区需要保留扩展余地
